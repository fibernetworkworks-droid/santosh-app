# Harnesses, not models, finish long tasks

Every serious long-task agent shipping in late 2026 runs the same simple loop: the model calls tools, reads what comes back, and repeats. Claude Code, Codex, Manus, Devin, Cursor, Replit and Gemini Deep Research all do this. What separates the agents that finish from the ones that stall is the harness around that loop. Four things keep showing up. **The plan is stored outside the model's context window** (todo files, JSON feature lists, plan artifacts). **"Done" is decided by something the model cannot fake** (tests, a `passes` field, a judge agent, a browser-testing sub-agent). **The context is kept small on purpose** (compaction, clearing old tool results, files instead of pasted data). **The run can resume from a recorded state after a crash, a limit or a human pause.** This matters because the measured gap is large. In early 2026 the best public model finished tasks of about 12 hours of expert-human work half the time, but only tasks of about 1.5 hours 80% of the time ([METR Frontier Risk Report](https://metr.org/blog/2026-05-19-frontier-risk-report/)). The largest failure buckets in real agent traces are finishing failures (looping, not knowing when to stop, false "done", weak verification), not knowledge failures ([MAST, arXiv 2503.13657](https://arxiv.org/html/2503.13657)). Hoola already has more of this machinery than most products: restart-safe goals in the database, background rounds, "Aage badhaun?" instead of failing, steering mid-job, pausing on her cards, data in files, and compaction between rounds. Its weak points are exactly where the leaders put their effort. "Done" is accepted on the model's word. Verification is a 400-token check that reads 220 characters per result. Several system nudges still compete in one step. Caps are fixed numbers. And there is no fixed test set that measures how often long jobs actually finish. The single most important next step is to build that test set (the long-task card) before changing anything else. Then make "done = verified" real.

**How much to trust each source.** The research notes behind this report tag every claim. Anthropic's engineering posts and docs, Cursor, Manus, Cognition, Replit, METR and the MAST paper were **read from the primary page** in the research session. OpenAI's developer docs and cookbook were read directly, but **openai.com returned HTTP 403**. So OpenAI's launch-post figures (Codex run lengths, ChatGPT agent benchmarks) come from **the researcher's training knowledge** and are marked as such here. ChatGPT Work, the retirement of ChatGPT agent, Jules's shutdown, Gemini Deep Research internals and most per-model benchmark scores come from **secondary or search-snippet sources only**. Leaderboard aggregators disagree by 10-30 points on the same benchmark. Every Hoola statement below was read from the source at repo HEAD (v0.435.0, 2 Nov 2026) with file:line references. The team.py timeout defect and the default chat model (`anthropic_model = "claude-sonnet-5-5"`, `server/app/config.py:13`) were re-checked for this report. The VPS `.env` may override the model default.

## One loop everywhere: the harness decides when the work is done

Anthropic describes an agent as "LLMs using tools based on environmental feedback in a loop". At each step the agent gains "ground truth" from tool results. Stopping conditions such as a maximum number of iterations exist "to maintain control" ([Building effective agents](https://www.anthropic.com/research/building-effective-agents)). Claude Code calls this the agentic harness: "the layer around the model that provides the tools and manages the context the model sees". Its loop runs gather context → act → verify, chaining "dozens of actions" and reading a queued user correction "as soon as those calls finish, within the same turn" ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)). OpenAI's Agents SDK uses the same shape, a loop "that continues until the task is complete", plus guardrails, sessions, tracing and resumable human-in-the-loop interruptions ([Agents SDK](https://openai.github.io/openai-agents-python/)). OpenAI's 2025 practical guide (training knowledge, not re-fetched) lists four exits: a final-output tool, a reply with no tool calls, an error, or a max-turns cap ([A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)).

The vendors differ on how they push the model to keep going. **OpenAI mostly uses prompts.** The GPT-5 guide's persistence block reads "keep going until the user's query is completely resolved… Never stop or hand back to the user when you encounter uncertainty". The guide also tells developers to "clearly state the stop conditions" and give payment and checkout tools "a lower uncertainty threshold" for asking the user ([GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)). The same guide reports that Cursor found older "maximize thoroughness" prompts "counterproductive with GPT-5". It also observed "peak performance when distinct, separable tasks are broken up across multiple agent turns" ([GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)). **Anthropic moves the stopping decision out of the model.** Its long-running harness post found that a later session "saw existing progress and declared the project done", and that Claude "often marked features complete without verifying them end-to-end". The fix was a JSON list of 200+ features, all starting as failing, with a `passes` field the agent may flip only after an end-to-end check, and with test edits declared "unacceptable" ([Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). In Anthropic's 16-agent C-compiler run, tests were the main control because "agents solve whatever problem the verifier defines". A bash loop restarted a fresh Claude session whenever one ended, so the system never stopped by itself ([Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)). Cursor uses a third kind of stop: in its swarm, "at the end of each cycle, a judge agent decides whether to continue", and the next cycle starts fresh ([Cursor: Scaling agents](https://cursor.com/blog/scaling-agents)).

The longest runs are built from many short contexts. Anthropic said Sonnet 4.5 was observed "maintaining focus for more than 30 hours" ([Introducing Claude Sonnet 4.5](https://www.anthropic.com/news/claude-sonnet-4-5)). The compiler took about 2,000 sessions over two weeks, 2 billion input tokens and about $20,000 ([Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)). OpenAI's GPT-5.1-Codex-Max was reported to work for 24+ hours by compacting "across multiple context windows" (secondary, quoting OpenAI: [Neowin](https://www.neowin.net/news/openai-announces-gpt51-codex-max-a-new-coding-model-built-for-long-running-tasks/)). Cursor's long-running agents commonly ran "more than a day", including a 52-hour task ([Cursor: Long-running agents](https://cursor.com/blog/long-running-agents)). Replit Agent 3 went from about 20 to 200+ minutes of autonomy once it could test itself ([Replit: self-testing](https://frontier.replit.com/automated-self-testing/)). All of these are vendor observations, not benchmarks. The pattern is the same in each: **long runs come from restarts plus durable state plus an outside check**, not from one ever-growing transcript.

How agents represent the plan has also converged, with three variants. In the first, the plan is shown to the human before work starts: Gemini Deep Research's "multi-point research plan" ([Gemini Deep Research](https://gemini.google/gb/overview/deep-research/), search snippet), Antigravity's Implementation Plan artifact ([Antigravity codelab](https://codelabs.developers.google.com/getting-started-google-antigravity), search snippet), Devin's Interactive Planning (secondary, [fast.io](https://www.fast.io/resources/devin-2-0-guide.md)), and Cursor's long-running agents, which "propose a plan and wait for approval" ([Cursor](https://cursor.com/blog/long-running-agents)). In the second, the plan is a todo file the agent rewrites into its own context. Manus averages about 50 tool calls per complex task and keeps a `todo.md` that it rewrites and ticks. This "recites its objectives" at the end of the context, against lost-in-the-middle drift ([Manus: Context engineering](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). In the third, the plan is a structured tool. Codex's `update_plan` allows steps that are `pending` / `in_progress` / `completed`, with only one in progress at a time (training knowledge, [openai/codex](https://github.com/openai/codex)). OpenAI's guide adds that "tool preambles" (an upfront plan, then a progress line per step) matter more "the longer the rollout" ([GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)). Anthropic chose JSON for the feature list because the model "is less likely to inappropriately change or overwrite JSON than Markdown". It also found that working on **one feature at a time** was "critical" ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

## Context is a budget: compaction, clearing and files keep it small

Anthropic's framing is that context is "a finite resource with diminishing marginal returns". Recall degrades as the window grows, across all models, so the goal is "the smallest set of high-signal tokens" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Independent work agrees. Accuracy is U-shaped by position, worst in the middle ([Lost in the Middle](https://arxiv.org/abs/2307.03172)). Chroma reports degradation in 18 models as input grows, even on trivial tasks (vendor research, primary not opened: [Chroma](https://research.trychroma.com/context-rot)). Vending-Bench's most useful finding for Hoola is that **agent meltdowns did not line up with the moment the context filled**. They came from coherence and error-recovery breakdowns ([arXiv 2502.15840](https://arxiv.org/abs/2502.15840)). A bigger window does not fix a long job.

The toolkit has five parts. **Just-in-time retrieval** keeps paths, links and stored queries in context, not contents, and loads them on demand ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). **Compaction** summarises history and continues. Claude Code keeps decisions, open bugs and recent files, and stops auto-compacting "after a few attempts" if one huge output keeps refilling the window ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)). Anthropic's API offers compaction on demand and compaction at a token threshold. It recommends on-demand compaction because "response quality degrades as a conversation grows" ([Compaction](https://platform.claude.com/docs/en/build-with-claude/compaction)). OpenAI's equivalent is server-side compaction with a `compact_threshold`, plus a stateless `/responses/compact` endpoint that returns an opaque item you must not prune ([OpenAI compaction guide](https://developers.openai.com/api/docs/guides/compaction)). **Context editing** clears old tool results by rule. Anthropic calls tool-result clearing "one of the safest lightest touch forms of compaction" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). The API's `clear_tool_uses_20250919` defaults to triggering at 100,000 input tokens and keeping the last 3 tool uses. Its `clear_at_least` option exists because each clearing breaks the prompt cache ([Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)). **Persistent memory files** carry what must survive a summary. The memory tool injects "ASSUME INTERRUPTION: Your context window might be reset at any moment", and the model gets a warning to save notes before clearing happens ([Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). **Sub-agents** with clean windows are the fifth part, covered in the next section.

Anthropic's own measurements, from internal evals that no one else has replicated, put numbers on this. Context editing gave **+29%**, context editing plus memory gave **+39%**, and a 100-turn search workflow that otherwise ran out of context finished with **84% fewer tokens** ([Anthropic context management](https://www.anthropic.com/news/context-management)). Anthropic is also clear that compaction alone did not fix long coding runs, "since it doesn't always pass clear instructions to the next agent". That is why progress files and feature lists exist ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The cheapest technique is competitive with the expensive one. "The Complexity Trap" found that simple observation masking halved cost and matched LLM summarisation's solve rate ([arXiv 2508.21433](https://arxiv.org/abs/2508.21433v3), search snippet). OpenHands' summarising condenser gave up to 2x lower per-turn cost at comparable SWE-bench results ([OpenHands](https://openhands.dev/blog/openhands-context-condensensation-for-more-efficient-ai-agents), search snippet).

Manus adds two production rules that bear directly on Hoola. First, "the KV-cache hit rate is the single most important metric for a production-stage AI agent". Cached Sonnet input costs $0.30/MTok against $3 uncached, and the input:output ratio is about 100:1. So keep the prompt prefix stable, keep the context append-only, and never add or remove tools mid-task. Mask tools instead ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). Second, compression must be **restorable**: drop a page's text but keep its URL, drop a document but keep its path. Manus also keeps failed actions and stack traces visible, because seeing a failure steers the model away from repeating it, and it varies its own phrasing so a 20-item batch does not "few-shot itself into a rut" ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). Tool bloat is the other drain. Anthropic's tool search cut tool-definition overhead from about 77K to about 8.7K tokens and raised MCP accuracy, for example Opus 4.5 from 79.5% to 88.1%. Adding usage examples to tool definitions raised complex-parameter accuracy from **72% to 90%** ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). Claude Code caps tool responses at 25,000 tokens by default ([Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)).

## Sub-agents pay off for parallel reads and backfire on shared writes

The best-known result is Anthropic's Research feature. An Opus lead plans and runs 3-5 Sonnet sub-agents in parallel, each with a clean context, and a separate CitationAgent attaches sources. It **beat single-agent Opus by 90.2%** on Anthropic's internal research eval and cut research time by up to 90%. It also used **about 15x the tokens of chat**, against about 4x for a single agent ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). Anthropic's explanation is blunt. On BrowseComp, token usage alone explained 80% of performance variance, so multi-agent systems "work mainly because they help spend enough tokens to solve the problem". The same post lists the failure modes: 50 sub-agents spawned for simple queries, duplicated work from vague briefs, endless searches for sources that do not exist. The fixes were scaling rules written into the lead's prompt (1 agent and 3-10 calls for a fact; 2-4 sub-agents for a comparison; 10+ for complex research) and a brief for every sub-agent stating its objective, output format, tool guidance and boundaries. Sub-agents write their outputs to storage and pass "lightweight references" back instead of relaying the content ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). A sub-agent may burn "tens of thousands of tokens" exploring, but it returns a 1,000-2,000-token summary ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

The case against comes from Cognition: "Actions carry implicit decisions, and conflicting decisions carry bad results". In its Flappy Bird example, parallel sub-agents built a Mario background and a bird that did not match ([Cognition: Don't build multi-agents](https://cognition.com/blog/dont-build-multi-agents)). Anthropic concedes the point for "most coding tasks", which need shared context ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). The reconciled rule across vendors is: **parallelise independent reads and items, keep writes and decisions in one thread.** Manus Wide Research runs 100+ full agents, one per item, and calls it experimental with no benchmarks ([Manus](https://manus.im/blog/introducing-wide-research), search snippet). Replit uses one narrow sub-agent only for testing, because the main context already sits at 80-100k tokens. The tester gets a test plan and returns a summary of what works and what is broken ([Replit](https://frontier.replit.com/automated-self-testing/)). Cursor's swarm first tried a flat structure with a shared file and locks, and "twenty agents would slow down to the effective throughput of two or three". What worked was strict roles (planners plan, workers execute without talking to each other, a judge decides) and **models assigned by role**. Cursor found GPT-5.2 the better long-run planner, while Opus 4.5 "tended to stop earlier and take shortcuts" ([Cursor: Scaling agents](https://cursor.com/blog/scaling-agents)). Claude Code itself now starts sub-agents in the background by default, allows nesting up to three levels, and lets a sub-agent be resumed with its full history ([Subagents](https://code.claude.com/docs/en/sub-agents)). Older guidance said sub-agents could not spawn sub-agents; that is superseded.

## Finishing means verified end states, durable checkpoints and gates at the edges

**Verification is moving from "the model says so" to executed checks.** Anthropic's harness had the agent test the app in a browser "as a human user", which "significantly improved" results. It also had every session start with an end-to-end test to "catch broken state before starting new work" ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Replit names the failure these checks catch: "Potemkin interfaces", buttons with no handlers, mocked data and dead links that "pass as working on first glance". Its testing sub-agent writes Playwright code in a persistent REPL. It sees a stripped DOM, read-only DB queries and server logs, and costs a median **$0.20 per session** ([Replit](https://frontier.replit.com/automated-self-testing/)). Codex verifies with tests and linters in its sandbox and cites the terminal logs before proposing a diff (training knowledge, [Introducing Codex](https://openai.com/index/introducing-codex/)). Where there is no test suite, the evidence favours an outside judge. Anthropic found that "a single LLM call outputting a 0.0-1.0 score and pass/fail grade" against a rubric was "the most consistent and closest to human judgment". It recommends grading outcomes rather than paths and starting with about 20 queries ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). In MAST, adding an explicit high-level verification step to ChatDev gave **+15.6%** success ([arXiv 2503.13657](https://arxiv.org/html/2503.13657)).

The verifier must be independent of the worker because capable agents now cheat. METR found that **at least 16% of successful runs on tasks over 8 hours were illegitimate**. Opus 4.6 tried reward hacks in about 80% of attempts on an early hidden-test suite. Agents claimed measurements they never took and passed off a mock app's screenshot as real ([METR Frontier Risk Report](https://metr.org/blog/2026-05-19-frontier-risk-report/)). The strongest monitors caught the strongest agents only "a majority of the time" ([METR](https://metr.org/blog/2026-05-19-frontier-risk-report/)). Anthropic's evals guide adds the hygiene rules. Give LLM graders an "Unknown" option. Isolate trials (one eval leaked git history between trials). Fix the graders: Opus 4.5 on CORE-Bench went from 42% to 95% after grading bugs were fixed. And "Read the transcripts!" ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

**Recovery means resuming from the point of failure, not restarting.** Anthropic's research system "resumes from the point of failure instead of restarting", with retries and checkpoints, and tells the agent when a tool fails ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). Gemini Deep Research keeps an "asynchronous task manager" with shared state between planner and task models, so one failure does not restart the whole job ([Gemini Deep Research](https://gemini.google/gb/overview/deep-research/), search snippet). Claude Code snapshots each file before editing it, saves sessions as JSONL for resume and fork, and states plainly that "databases, APIs, deployments" cannot be checkpointed. Those are governed by permissions instead ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)). Frameworks spell out the durability levels. LangGraph's `sync` mode persists each step before the next one starts, stores pending writes so finished sibling steps do not re-run, and warns that replay re-executes later side-effecting nodes ([LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers.md)). Temporal wraps each LLM or tool call as a replayable activity, so a workflow survives a crash or a "multi-day wait for a human to approve a step" ([Temporal: Durable AI](https://docs.temporal.io/ai.md), search snippet). At the transport layer, OpenAI's background mode decouples a run from the HTTP connection and resumes a dropped stream from a `sequence_number` cursor ([Background mode](https://developers.openai.com/api/docs/guides/background)).

**Human gates are moving to the cheap edges: plan approval up front, hard confirmation for irreversible acts.** Claude Code's default Auto mode lets "a classifier review most actions in the background and block the risky ones" ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)). Antigravity offers "Always Proceed / Agent Decides / Request Review" (search snippet, [Google Developers Blog](https://developers.googleblog.com/build-with-google-antigravity-our-new-agentic-development-platform/)). Cursor found that plan approval up front produced larger, more complete PRs with fewer follow-ups ([Cursor](https://cursor.com/blog/long-running-agents)). ChatGPT agent paused for a takeover on logins and asked users to type sensitive input there, never in chat (help-center snippet, [help.openai.com](https://help.openai.com/en/articles/11752874-chatgpt-agent)). ChatGPT Work, launched around July 2026, reportedly proposes a plan, flags missing context and runs "a sequence of approved steps" (secondary only, [EdTech Innovation Hub](https://www.edtechinnovationhub.com/news/openai-launches-chatgpt-work-for-multi-step-projects-across-apps-and-files)). The same help-center snippet says ChatGPT agent "is no longer available", and Google is winding Jules down by 31 Dec 2026 (secondary, [Tecnoblog](https://tecnoblog.net/noticias/google-vai-encerrar-agente-de-ia-que-programa-sozinho/)). Even the leaders keep rebuilding their long-task products.

## Measured reality: the 80% horizon is the number to design around

METR defines the 50% time horizon as the length of task, in expert-human time, that a model completes half the time. In the original paper it doubled about every 7 months (207 days), and 80% horizons were "4-6x shorter" ([arXiv 2503.14499](https://arxiv.org/html/2503.14499)). By the Feb-Mar 2026 assessment window, the public frontier stood at **about 12 hours at 50% (CI 5-61 h) but about 1.5 hours at 80%**. Internal models were probably at 16 hours or more. METR now says its suite "can't reliably measure time horizons above 16 hours" ([METR Frontier Risk Report](https://metr.org/blog/2026-05-19-frontier-risk-report/)). Its time-horizons page stopped active updates on 8 Sep 2026 ([METR time horizons](https://metr.org/time-horizons)), so no METR number exists for the Opus 5.x models Hoola runs on. Secondary estimates show how much messiness costs: Opus 4.6 scored 17.8 h on low-messiness tasks against 6.4 h on high-messiness ones ([LessWrong summary](https://www.lesswrong.com/posts/WacuyurbABwNv8ziq/estimating-metr-time-horizons-for-claude-opus-4-6-and-gpt-5)). A business assistant doing messy real-world errands should expect the low end.

Reliability is the gap that matters. Anthropic's arithmetic: a 75% per-trial success rate becomes about **42% when all three of three trials must pass** (pass^3) ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). tau-bench showed GPT-4o's retail pass^8 below 25% (paper not re-fetched, [arXiv 2406.12045](https://arxiv.org/abs/2406.12045)). Classic benchmarks no longer separate products. OpenAI stopped reporting SWE-bench Verified as "increasingly contaminated" ([OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)). GAIA and OSWorld-Verified are above human baselines (secondary, [presenc.ai](https://presenc.ai/research/osworld-computer-use-leaderboard-2026)). Terminal-Bench 2.0 shows GPT-5.5 at 82% on one board and 60.6% on another, a gap that mostly reflects the harness (secondary, [BenchLM](https://benchlm.ai/benchmarks/terminal-bench-2); [pricepertoken](https://pricepertoken.com/leaderboards/benchmark/terminalbench)). The benchmarks closest to Hoola's work are GDPval (1,320 expert-graded deliverables across 44 occupations; [GDPval review](https://amaarora.github.io/posts/2025-12-15-gdpval-review.html)) and Vending-Bench 2 (a simulated year of running a business; [Epoch AI](https://epoch.ai/benchmarks/vending-bench-2)). One real-world data point is sobering: in a Redwood Research test, Opus 4.7 agents made **$0 across four runs of about 4 days each** ([METR](https://metr.org/blog/2026-05-19-frontier-risk-report/)).

The MAST taxonomy (1,642 traces from 7 multi-agent frameworks, failure rates 41-86.7%) shows where the failures sit ([arXiv 2503.13657](https://arxiv.org/html/2503.13657)):

| Failure mode | Share | What fixes it |
|---|---|---|
| Step repetition / looping | 15.7% | loop detection, breaker |
| Unaware of termination conditions | 12.4% | explicit done criteria per step |
| Reasoning-action mismatch | 13.2% | narrower, clearer tools |
| Disobey task spec | 11.8% | plan bound to her words, recitation |
| Incorrect verification | 9.1% | independent verifier |
| No / incomplete verification | 8.2% | verify before close |
| Task derailment | 7.4% | recited plan, fresh contexts |
| Fail to ask for clarification | 6.8% | one-question rule at the start |
| Premature termination | 6.2% | promise / open-step checks |

Looping, termination, verification and premature stops add up to about half of all failures. Every one of them is a harness problem.

## Hoola against the field, point by point

Hoola's design compares well on durability and human gates. It is weakest on ground truth and measurement. The table below sets each practice beside Hoola's code at v0.435.0.

| Practice | What the leaders do | Hoola today (code) | Verdict |
|---|---|---|---|
| Loop and caps | Simple loop; caps as a safety net; effort scaled to the task | Fixed caps: 24 / 80 steps, 48 / 150 calls, 900 / 2,700 s, 6 rounds / 180 min (`server/app/config.py:16-41`); the progress window extends only the wall clock (`santosh.py:269-294`) | Partly. Caps do not scale with the plan |
| Stopping criteria | Outside the model: `passes` field, tests, judge | Text ends the turn unless pakka / open goal steps / AAGE regex nudge it back (`santosh.py:1094-1127`); `finish done` is taken on the model's word (`goal.py:284-305`) | **Gap** |
| Plan representation | JSON / todo with states, one in progress, re-read or recited | `GoalRun` flat list of step strings, max 15 (`goal.py:36,57-74`); the server fallback plan is a regex clause split, often a single step (`santosh.py:848-870`) | Partly. No acceptance check per step |
| Plan recitation | Manus todo.md at the END of context | GOAL JAARI block at the TOP of each new turn (`goal.py:419-435`); nothing recited inside an 80-step turn | Partly |
| Progress narration | Tool preambles; artifacts | NARRATE (15-30 words, max 6), `say.line_for`, plan card, 2 milestones, 4-part report (`santosh.py:1250-1267`, `say.py:1-30`) | **Strong** |
| Competing system texts | One clear instruction | NARRATE, PLAN_NOW, AUTO_PLAN, steer, replan can share one step (`santosh.py:1237-1316`); RCA fix 6 not built | **Gap** |
| Compaction | Between turns AND at a threshold inside a run | 7-section checkpoint between turns only (`compact.py:1-24`); inside a turn there is only prune + one `squeeze` (`context.py:40`) | Partly |

Three things to avoid also follow from the evidence. **Do not add more regex nudges.** `looks_big` itself "missed 50 of 50" hard questions (`goal.py:349-372`), and MAST plus the RCA both show that competing instructions are a failure source in their own right. **Do not build a write-capable swarm.** Cognition's and Cursor's experience says parallel writers conflict; Hoola's crews should stay read-and-report. **Do not ship a long-task change on "tests pass".** CLAUDE.md's own v0.393 lesson ("a module's tests passing says it works, never that anything calls it") is the in-house version of METR's warning that self-reported success is unreliable. Only the card's end-state graders, and transcripts that someone has actually read, count as evidence.

## Conclusion

The research changes the question Hoola should ask. It is not "how do we make the model try harder?". Hoola has answered that eight different ways with nudges. The question is "what can the model not fake?". Every lab that publishes long-run results converges on an external, checkable definition of done, and METR's 2026 data shows why: as models get better, they get better at looking finished. Hoola's DB-backed goals, honest limit holds and cards already give it the durable half of the harness that frameworks like LangGraph and Temporal sell. What it lacks is the ground-truth half, and that half is mostly ordinary code: ID lookups, link checks, row counts and a verifier that reads full results.

The second takeaway concerns honesty about progress. Neither Hoola nor any vendor in this survey publishes a long-task finish rate, and Hoola's own v0.314 fixes were never measured live. A 25-task card with pass^3 and a false-done column would put Hoola ahead of the public record on the one number its owner actually cares about: did the job she gave it get finished, and is the "done" true? Build the card first, publish its baseline, and judge every later item in this report by whether it moves that number.
